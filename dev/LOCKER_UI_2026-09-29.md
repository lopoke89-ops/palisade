# Locker UI validation — v0.9.3.3 candidate

Compared against v0.9.3.2 (`39ec2b4`) on September 29, 2026. The candidate is local, uncommitted, and unpublished. No server migration or network protocol change accompanies it.

## Result

Milestone items appear exclusively in MILESTONES. Each ordinary category has visible standard/non-case unlocks, then one disclosure per nonempty case collection. Collection headers show owned/total counts. More than one collection can stay open, and their state survives category switching and equip refreshes for the current page session. Collapsing removes the item canvases and observer registrations; expansion creates only that collection's tiles. Mounted tiles update in place when ownership/equipment changes. Newly equipped case rewards reveal and focus their item in the matching collection.

## Focused checks

The build passed using the bundled Python/Pillow runtime and repository Terser. These eight browser checks passed with installed Chrome:

- `locker_collections`: exact catalog membership across all five categories; all milestone items/progress retained; no canvases in collapsed case sections; multiple disclosures, keyboard Enter/Space and touch; equip focus/scroll retention; ownership-count refresh; case-result EQUIP navigation; no horizontal text/page overflow at 390×844, 844×390, and 1280×900.
- `milestones`, `flagcase`: existing ladder, unlock, Flag case purchase, and equip checks, adapted to Milestones-only browsing and collapsed Flag collections.
- `accounts`: mocked account and equip flows, including server-backed case-result equip.
- `locker_fit`, `cosmetics`: character/FX fit and cosmetic catalog/rendering checks.
- `csp`, `taborder`: production/debug policy loading and keyboard navigation checks.

The `locker` targeted group is available in both runners. No combat or full-suite run was needed. Browser account tests use mocked endpoints and do not change live data.

## Phone-sized comparison

Three alternating before/after pairs used fresh Chrome pages at 390×844, device scale 2, with software drawing on the same Windows PC. The baseline was the pre-edit v0.9.3.2 debug page; the candidate was the rebuilt debug page. Each opened SKINS, scrolled the tabs into view, and sampled Chrome's total TaskDuration for the first 1.2 seconds plus a subsequent 2.5-second interval. This includes the page's background animation and is not an isolated GPU/frame-rate or physical-phone test.

| Metric | v0.9.3.2 | v0.9.3.3 candidate |
|---|---:|---:|
| Initially mounted Skins tiles/canvases | 72 | 4 |
| Initial Skins grid height, CSS pixels | 7,827 | 660 |
| Task CPU in first 1.2 seconds, median | 256.1 ms | 187.4 ms |
| First-window CPU range | 240.6–356.1 ms | 155.2–223.6 ms |
| Settled Task CPU per second, median | 104.6 ms | 89.8 ms |
| Settled CPU range per second | 93.8–159.1 ms | 63.6–93.6 ms |

The deterministic improvement is less initial DOM/canvas allocation and much less scrolling. The CPU measurements support a reduction in this setup but are too limited to establish phone battery use or frame-rate gains. Remaining v0.9.3.2 physical-phone movement and live account/PWA verification are not closed by these checks.
