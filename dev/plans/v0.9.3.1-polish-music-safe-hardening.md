## 0. Streamline testing before making feature or security changes

First, map the existing tests to the behavior they cover, then make it easy to run a small relevant set. The runner in `dev/test/run_all.sh` originally accepted `TESTS` but defaulted to all 26 browser tests; the implemented workflow adds targeted groups and retains the expanded 29-test full suite on demand. Select tests by the code and behavior changed:

- Cosmetic geometry or Locker rendering: cosmetic, wardrobe/Locker, and affected screen-size checks. Do not run gunplay tests for cosmetic-only edits.
- Music or audio routing: music/audio and the affected menu, build, and raid transitions. Do not run unrelated cosmetic or gunplay tests.
- Weapons or combat changes: gunplay/combat and directly affected network tests.
- Security validation: focused malformed-input, honest-player, and relevant multiplayer/rejoin checks for the specific rule changed.

Run the smallest meaningful set after each change. Add a focused regression test only when it catches a real failure mode that existing tests miss; avoid tests that merely mirror the implementation. Run broader smoke or full-suite checks only when shared systems change, targeted results point to a wider risk, or the release candidate needs them for a concrete reason. Record which checks were run and why. Keep the test-selection workflow in place before starting items 1–4.

## 4. Implement only low-risk security hardening

Review the existing v0.9.3.1 hardening backlog against the actual code. Implement a small, clearly safe subset that improves input validation without changing legitimate gameplay, account identity, rewards, saved data, or the network protocol. A reasonable starting point is rejecting non-finite, malformed, or impossible guest action values at the host boundary while preserving valid inputs. Assess each candidate for false positives and phone performance before including it. A movement speed cap is optional only if honest play under lag and low frame rates shows it is safe.

Defer changes that require a Supabase migration, reward-claim rewrite, import-trust policy, account/guest identity redesign, room protocol bump, or other broad behavior change. If a seemingly small fix causes honest players to be rejected, alters gameplay, or cannot be validated confidently, leave it out and document the reason. Do not modify live Supabase data or apply a migration as part of this patch.
