## Deployment order

1. **Check the base.** `main` is still at or after `ca90257`, and the live function is v0.10.1. Run `select count(*) from casino_tables where open` and note the open tables (they keep working).
2. **Apply the migration** (SQL editor or migration tool). It is safe to run twice. Verify:
   - `select station from casino_tables limit 1` works;
   - `select count(*) from casino_seats` = the number of seated accounts;
   - `has_function_privilege('authenticated','public.casino_step(bigint,integer,jsonb,uuid[],boolean,jsonb,jsonb,jsonb)','execute')` is false.
3. **Deploy the edge function** `dev/supabase/functions/tables/`. Smoke test with a test account:
   - a lobby request;
   - a blackjack sit (an old table opens and plays);
   - a slot spin carrying `opId` (it settles), then the same request again (`replay: true`, no second debit);
   - `select * from casino_ops order by created_at desc limit 3`.
4. **Publish the site:** merge to `main`; GitHub Pages builds in about 1–15 min. It is live only when the footer reads **v0.10.3** and `sw.js` lists the current asset URLs.
5. **Next day:** `casino_books` has the new columns filled and `ok = true`.

## Rollback

Receipts and history are never deleted. Every settled round stays in `casino_hands`, and every shard move in `casino_ledger`.

1. **Website:** revert `main` to the v0.10.1 commit (`ca90257` content). Players get v0.10.1 on their next load.
2. **Drain the new games before touching the function.** The v0.10.1 engine can't run baccarat, craps or machine sessions.
   - With the v0.10.3 function still live, send casino `lobby` requests: each one sweeps tables idle for 3 minutes, stands their players up (shards home) and rolls out any craps bets left working, up to 60 rolls a batch.
   - Repeat until `select count(*) from casino_tables where open and game in ('ba','cr','sl','pk')` is 0.
   - Machines and baccarat close within minutes of the last player leaving. Craps closes once its working bets are decided; no bet is refunded or cut short.
3. **Redeploy the v0.10.1 function** (from `ca90257`). It uses `casino_open` / `casino_commit`, which still exist.
4. **Leave the migration in place.** It is additive, and the old function ignores the new columns and tables. Reverting the schema isn't needed and would discard the operation records.

## Outstanding wagers across the change

- **Function deploy:** a hand in progress during the deploy finishes under the new engine. Its rules are the same; only the review timing differs.
- **Rollback:** drain first (step 2), so no new-game wager is ever left on a table the old engine can't run.
- **Retired rules versions:** keep support for a rules version until no open table uses it. `select distinct game from casino_tables where open` tells you.
